# CQA: автоматическая оценка качества работы операторов
# Название команды: aleb

Прототип для Freedom Broker CQA Hackathon. Пользователь настраивает чек-лист, загружает диалоги (чаты и звонки, RU / KZ / EN) и запускает оценку оператора моделью. Система показывает баллы, объяснения и реплики-основания. Оператор может оспорить критерий, проверяющий принимает решение, итог пересчитывается.

- **Модель:** `gpt-6.1-sol` (OpenAI), reasoning effort `medium`, промпт `v2`.
- **Стоимость одной оценки диалога со всеми вызовами:** в среднем около **$0,012** (от $0,0114 до $0,0134 в разных измерениях, см. раздел 3). Один вызов модели на диалог, ремонтные вызовы в измерениях не понадобились. Около $1,2 на 100 диалогов, около 2 минут на 100 диалогов при 8 потоках.
- **Стек:** Python 3 / FastAPI / SQLite на сервере; интерфейс на чистых HTML, CSS и JavaScript (Web Components, без сборки).

Содержание: [1. Как запустить](#1-как-запустить) · [2. Что умеет система](#2-что-умеет-система-и-где-это-в-коде) · [3. Модель и стоимость](#3-модель-и-стоимость) · [4. ## 1. Как запустить

### Быстрый способ: Docker Compose

```bash
git clone <ссылка на репозиторий>
cd freedom-broker
cp .env.example .env        # впишите только OPENAI_API_KEY
docker compose up -d --build
```

Интерфейс: <http://127.0.0.1:8000/app/>, проверка: <http://127.0.0.1:8000/health>. База лежит в томе `cqa-data` и переживает перезапуск; `docker compose down -v` удаляет её вместе с томом. Логи: `docker compose logs -f`. Контейнер берёт переменные только из `.env`, а не из оболочки, поэтому старый `export OPENAI_API_KEY` ему не мешает. После правки `.env` выполните `docker compose up -d`, чтобы применить изменения.

Дальше всё как в разделе «Первый прогон за 5 шагов». Ручной запуск без Docker описан ниже.

### Требования (ручной запуск)

- Python 3.11 или новее (разработка шла на 3.14).
- Node.js 20 или новее нужен только для тестов интерфейса. Для запуска приложения не нужен.
- Ключ OpenAI с доступом к `gpt-6.1-sol` (без ключа приложение запускается, но оценки будут падать быстро со статусом `failed`).

### Шаги

```bash
git clone <ссылка на репозиторий>
cd freedom-broker

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
```

Откройте `.env` и заполните:

| Переменная | Что вписать |
|---|---|
| `OPENAI_API_KEY` | ключ OpenAI (секрет, в репозиторий не попадает: `.env` в `.gitignore`) |

Адрес API организаторов `CQA_API_URL` уже прописан в `.env.example`; для контрольного набора меняется только `group_id`.

Остальные переменные уже имеют рабочие значения по умолчанию (таблица в разделе 3).

Запуск сервера из корня репозитория:

```bash
uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

- Интерфейс: <http://127.0.0.1:8000/app/>
- Проверка состояния: <http://127.0.0.1:8000/health> (поле `llm.ready: true` означает, что ключ найден)
- Документация API (Swagger): <http://127.0.0.1:8000/docs>

База SQLite создаётся автоматически в файле `cqa.db` (путь меняется через `CQA_DB_PATH`). При первом запуске в неё записывается стартовый чек-лист из задания (8 критериев) из `backend/app/seed/checklist_default.json`.

> **Важно про ключ.** Переменная окружения процесса побеждает значение из `.env`. Если в оболочке остался старый `export OPENAI_API_KEY=...`, сервер возьмёт его, а не ключ из `.env`. Запускайте сервер так: `env -u OPENAI_API_KEY uvicorn backend.app.main:app --port 8000`.

### Первый прогон за 5 шагов

1. Откройте <http://127.0.0.1:8000/app/>. Роль по умолчанию «проверяющий» (reviewer): ей доступны все действия. Роль «оператор» может только подавать апелляции.
2. **Загрузите набор** во вкладке «Запуски»: по `group_id` (например, `DEV`) или из файла JSON в формате ответа организаторов. То же через API:
   ```bash
   curl -X POST http://127.0.0.1:8000/api/v1/datasets/import \
        -H 'Content-Type: application/json' -d '{"group_id": "DEV"}'
   ```
3. **Проверьте чек-лист** во вкладке «Чек-листы»: критерии, веса, шкалы, доступность N/A. Любая правка сохраняется как новая версия, старые оценки остаются привязаны к своей версии.
4. **Запустите оценку** во вкладке «Запуски»: выберите набор, версию чек-листа и модель, посмотрите оценку стоимости, нажмите запуск. Прогон можно остановить кнопкой «Остановить» (завершённые оценки сохраняются, незавершённые вызовы дорабатывают и стоят денег, остальные пропускаются). Одну оценку можно запустить и из карточки диалога.
5. **Откройте карточку диалога:** транскрипт, баллы, объяснения, реплики-основания (ссылка ведёт к нужному сообщению или фрагменту звонка), итог и результаты секций. Оспорить критерий: «Апелляция». Принять решение: очередь апелляций.

Демонстрационные диалоги DEV (набор из задания): `p1-ru-001` (чат, часть критериев N/A), `p1-ru-022` (грубое нарушение), `p4-ru-004` и `p4-ru-005` (звонки с записью).

### Контрольный набор и замена критерия (T0+23h)

1. Импортируйте контрольный набор с новым `group_id`, который сообщат организаторы (шаг 2 выше).
2. Запустите прогон на нём (шаг 4): при 8 потоках около 2 минут на 100 диалогов. Упавшие или спорные элементы перезапускаются кнопкой повтора в списке элементов прогона.
3. Для замены критерия откройте чек-лист, измените или замените критерий, нажмите «Сохранить». Новая версия применяется к выданным диалогам новым прогоном (выберите её версию). Итоги и баллы пересчитываются по новой версии, старая остаётся в истории.

### Файлы результатов для организаторов (`results/dev` и `results/prod`)

Формат JSON 1.0 из приложения к гайду: один файл `results.json` на набор, один объект на диалог, восемь критериев с кодами `contact`, `discovery`, `identification`, `consultation`, `empathy`, `dialogue`, `closure`, `critical`, `value` (`true` / `false` / `null` для N/A / число шкалы), `rationale`, `evidence_turns` (номера реплик с 1 по всему транскрипту), `final_score` и `critical_flag`. Диалог, который не удалось оценить, попадает в файл со `status: "error"` и причиной, а не с нулевой оценкой.

```bash
python scripts/export_results.py --set dev  --dataset DEV --team-name "<название команды>"
python scripts/export_results.py --set prod --dataset <group_id контрольного набора> --team-name "<название команды>"
git add results && git commit -m "Add results" && git push
```

Скрипт читает базу только на чтение (по умолчанию `cqa.db`, параметр `--db`), берёт оценки по дефолтной версии чек-листа (`--version-id` для другой), сверяет файл с форматом (все 8 критериев по одному разу, уникальные ID, `critical_flag` равен `critical`) и пишет `results/<dev|prod>/results.json`. Коды критериев назначаются по порядку критериев в чек-листе, поэтому при замене критерия нужно сохранить его позицию, а чек-лист должен содержать ровно 8 критериев и последним флаг грубых ошибок. В Docker базу сначала забирают командой `docker compose cp cqa:/data/cqa.db ./cqa.db`.

## 2. Что умеет система и где это в коде

### Контур 1: оценка

| Требование | Как реализовано |
|---|---|
| Создать чек-лист: критерии, формулировки, вес, тип ответа (да/нет, шкала, флаг грубого нарушения), N/A, шкалы | Конструктор чек-листа в интерфейсе (`frontend/src/components/cqa-checklist-builder.js`), версии, секции, привязка к каналам (чат и звонок), API `/api/v1/checklists`. Новый критерий применяется через настройки, в коде критериев нет |
| Оценить выбранный диалог, RU / KZ / EN, реплики бота и системные события как контекст | `POST /api/v1/conversations/{id}/evaluate`, пакетные прогоны `POST /api/v1/runs`; промпты и проверки в `backend/app/services/evaluator.py` и `prompts.py` |
| Показать ответ, баллы, вес, объяснение, реплику-доказательство; для пропущенного действия проверенный участок; для N/A причину; итог и секции | Карточка диалога. Модель обязана дать точные цитаты и `checked_range` (проверенный участок) для «Нет», `na_reason` для N/A. Код проверяет, что цитата дословно есть в указанном сообщении, иначе один ремонтный вызов, затем статус `needs_review` |
| Пересчёт с учётом веса, перераспределение веса при N/A, отдельная отметка грубой ошибки, округление из чек-листа | `backend/app/services/scoring.py`. Баллы считает код, не модель |

### Контур 2: работа с результатом

| Требование | Как реализовано |
|---|---|
| Карточка: из списка к транскрипту и результату, ссылка в обосновании ведёт к реплике или фрагменту звонка, прослушивание записи | Список и карточка диалога; встроенный плеер звонка с переходом к фрагменту (`/api/v1/conversations/{id}/audio`, `backend/app/services/audio_timing.py`) |
| Апелляция: критерий, комментарий, проверяющий видит спорную оценку, комментарий и фрагмент | Кнопка «Апелляция» на критерии, очередь апелляций (`/api/v1/appeals`) |
| Решение: подтвердить или изменить оценку с причиной, пересчёт итога, в карточке исходная оценка, решение и финал | `POST /api/v1/appeals/{id}/decision`; итог пересчитывается тем же `scoring.py`, в карточке видны исходная и финальная версии |

### Данные и формат

- Набор организаторов загружается по `group_id` (транскрипт сохраняется с исходными метками времени: `MM:SS` у чатов, ISO 8601 у звонков, роли client, operator, bot, system, `audio_url` у звонков).
- **Интерфейс как HTML-компоненты** для адаптации под Dynamics 365: каждый экран это Web Component с shadow DOM (`cqa-overview`, `cqa-conversation-list`, `cqa-conversation-card`, `cqa-appeal-drawer`, `cqa-appeal-queue`, `cqa-checklist-builder`, `cqa-eval-runs`). Атрибуты и события описаны в `frontend/src/register.js` и `events.js`, адрес API задаётся через `window.CQA_CONFIG.apiBase` (`frontend/config.js`). Страница `frontend/embed-test.html?c=cqa-conversation-card&record=<id>` показывает один компонент отдельно, как его покажет встраивающая страница.
- Регистрации и входа нет, роль переключается списком в шапке (проверяющий и оператор).

## 3. Модель и стоимость

**Модель:** `gpt-6.1-sol`, OpenAI Responses API со строгой JSON-схемой ответа, без `temperature`, `store: false`. Цена: $2 за 1 млн входных токенов, $0,1 за 1 млн кешированных входных, $10 за 1 млн выходных (рассуждение входит в выходные), без скидки Batch API.

**Стоимость одной оценки (все вызовы, фактические токены):**

| Измерение | Диалогов | Средняя стоимость | Источник |
|---|---|---|---|
| Боевой прогон через интерфейс (R-0003), набор DEV из задания | 65 | **$0,0114** (итого $0,743) | запрос к `cqa.db`, только чтение |
| Dev-набор, 2 повтора | 48 оценок | $0,0124 | `evals/runs/20261108-005254-gpt_sol_medium-dev` |
| Отложенный набор (невиданные данные) | 12 | $0,0134 (максимум $0,0188) | `evals/GPT_HOLDOUT.md` |
| Теневой прогон кода приложения на копии базы | 10 | $0,0124 | `evals/GPT_SHADOW.md` |

Средние токены на диалог: около 1300 некешированных входных, 1500 кешированных, 1000 выходных (с рассуждением). **Итого около $0,012 за оценку, около $1,2 на 100 диалогов.**

**Скорость:** среднее время одного диалога 9,5 до 9,8 с (p95 около 13 с). Пакет из 65 диалогов DEV на 8 потоках: 83 секунды, то есть около 2 минут на 100 диалогов. 0 ошибок, 0 `needs_review`, 0 повторов из-за лимитов на этом прогоне. Лимит OpenAI (5000 запросов и 1 млн токенов в минуту) при 8 потоках используется примерно на пятую часть.

**Как устроена оценка (одинаково в измерениях и в проде):**

- Один вызов модели на диалог, все критерии сразу, ответ строго по схеме.
- Код проверяет ответ: цитаты дословно из указанных сообщений, `checked_range` для «Нет» по да/нет, `na_reason` для N/A, допустимость N/A и значений шкалы, обоснование на русском.
- При ошибках проверки один ремонтный вызов с перечнем ошибок; если ошибки остаются, критерий получает статус `needs_review` и в баллы не входит.
- Отказ модели и обрезка по лимиту токенов сохраняются как `needs_review`, а не как ложный балл.
- Повторы 408, 409, 429 и 5xx с паузами; ошибки «нет кредитов» и неверный ключ останавливают весь прогон сразу (не повторяются как лимит).
- Ключ вымарывается из ошибок и логов; текст диалогов в журнал не пишется.

Цена в интерфейсе (`GET /api/v1/models`): пока нет измерений, показывается ориентир из настройки ($0,0125), затем измеренное среднее по истории оценок этой модели.

## 4. Сравнительная матрица eval

Выбор модели и промпта делался не на глаз, а на замороженном наборе и чек-листе с LLM-судьёй, измеряя качество, стоимость и задержку. Всё лежит в репозитории в JSON и воспроизводится (раздел «Как воспроизвести» ниже).

### Методика

- **Набор:** 36 синтетических диалогов (`evals/dataset.json`, карточка `evals/DATASET.md`, проверки `evals/DATASET_VALIDATION.md`): чаты и звонки, RU / KZ / EN, разной длины, с N/A, грубыми нарушениями и спорными случаями. 24 диалога «dev» (на них выбирали), 12 «holdout» (смотрели один раз в конце). Чек-лист заморожен (`evals/checklist_v2.json`, 8 критериев из задания).
- **Точность:** доля точных совпадений ответа с эталоном по 8 критериям; на 24 диалогах с 2 повторами это 384 ответа, с одним повтором 192. Две колонки: по исходной разметке и по исправленной. Исправление касается критерия 06 (шкала): оценку по 11 диалогам определил человек вслепую (на 9 она отличается от исходной) (`evals/review/adjudication_06.json`), потому что исходная разметка по 06 оказалась слишком щедрой. Исправленная колонка надёжнее.
- **Стоимость:** пересчёт по фактическим токенам и прайс-листу (`evals/prices.py`), без скидки Batch API. Включает ремонтные вызовы.
- **Задержка:** сумма времени вызовов на диалог в живом режиме; у прогонов Opus и Sonnet через Batch API задержка не измеряется (прочерк). У Opus 5.5 в боевой базе измерено 13,5 и 14,0 с.
- **Ремонт:** доля диалогов, которым понадобился второй вызов из-за ошибок проверки.
- **Судья:** Sonnet 5.5 сравнивает объяснения и цитаты с эталоном (шкала 0 до 10). Для судьи важна оговорка из раздела 5 (эталон писала сама gpt-6.1-sol).

### Что показывает матрица

3. **Правило v2 убрало ремонтные вызовы.** У Opus на промпте v1 35 % диалогов (17 из 48) требовали второго вызова, всегда из-за одного: «Нет» по критерию 05 без указанного проверенного участка. С правилом v2 ремонтных вызовов 0 из 48 и у Opus, и у gpt.

### Как воспроизвести

Все команды запускаются из корня репозитория; по умолчанию это пробный прогон без отправки запросов, реальный запуск требует `--execute` и `--max-spend`. Для экспериментов нужны `OPENAI_API_KEY` (gpt), `LLM_API_KEY` (Anthropic и судья) и `OPENROUTER_API_KEY` (Jev) в `.env`, зависимости из `requirements-evals.txt`.

```bash
pip install -r requirements-evals.txt
python scripts/eval.py run gpt_sol_medium --split dev --reps 2 --mode live --max-spend 1.5            # пробный прогон
python scripts/eval.py run gpt_sol_medium --split dev --reps 2 --mode live --max-spend 1.5 --execute  # реальный
python scripts/eval.py judge <id прогона> --max-spend 1.5 --execute
python scripts/eval.py report <id прогона>
python scripts/eval.py ledger                                                                         # расходы
```

Определения вариантов (модель, промпт, workflow, усилие) лежат в `evals/variants.json`, результаты каждого прогона в `evals/runs/<id>/` (`meta.json`, `results.json`, `judge.json`), расходы в `evals/ledger.json`. Подробные итоговые отчёты: `evals/GPT_DEV_GATE.md`, `evals/GPT_HOLDOUT.md`, `evals/GPT_SHADOW.md`. Теневой прогон на копии базы: `python scripts/shadow_compare.py --db <копия> --version-id 2 --max-spend 0.2`.

## 5. Ограничения и честные оговорки

1. **Эталон писала та же модель.** Ожидаемые ответы и обоснования 36 синтетических диалогов сгенерировала `gpt-6.1-sol`. Поэтому её лидерство в колонке «Судья» (9,21 против 8,70) завышено: она ближе к эталону по формулировкам. По точным ответам после поправки на критерий 06 она равна Opus, и именно на это опирался выбор.
2. **Малая выборка.** 24 диалога для настройки и 12 для проверки показывают грубые сбои, но не тонкие различия. Критерий 06 на отложенных диалогах размечен без поправки. Критерии 02, 04 и 07 человеком не проверялись.
3. **Один человек разметки, синтетические диалоги.** Независимой повторной разметки нет. Настоящие диалоги организаторов (DEV) оценивались только в теневом режиме на 10 диалогах и затем целиком боевым прогоном (65), но без эталонных ответов.
4. **Критерий 02 и N/A.** В теневом прогоне на 3 из 10 диалогов gpt ставил N/A там, где Opus отвечал «Да» или «Нет». N/A убирает вес критерия из итога, поэтому итоговый балл таких диалогов смещается. Такие случаи стоит выборочно прочитать и при необходимости уточнить формулировку N/A в чек-листе.
5. **Данные уходят второму поставщику.** Для оценки полный текст диалога отправляется в OpenAI (с `store: false`). Срок хранения на стороне OpenAI для мониторинга злоупотреблений зависит от настроек организации и здесь не проверялся. Перед использованием настоящих клиентских данных проверьте настройки данных организации (нулевое хранение). Запасной вариант отправляет тот же текст в Anthropic или AWS Bedrock.
6. **Данные синтетические, оценка изолирована.** Все расходы на эксперименты учитывались отдельно (`evals/ledger.json`, бюджет на Anthropic $10); расходы на OpenAI и на генерацию набора в этот бюджет не входят.
